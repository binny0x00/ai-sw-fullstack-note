# 01. 전체 성능 평가 계획

## 1. 평가 목적

이 평가는 AI 응용 기술을 활용한 게시판이 실제 서비스 구조로 동작하는지
확인하기 위한 것입니다.

평가의 핵심 질문은 다음입니다.

- 일반 게시판 기능이 안정적으로 동작하는가?
- 관리자 권한 사용자만 AI 검토 기능을 사용할 수 있는가?
- RAG 검색 결과가 담당자 답변에 실제로 도움이 되는가?
- Agent가 문의 유형과 처리 방향을 일관성 있게 판단하는가?
- GitHub Issue 생성은 담당자 승인 후에만 실행되는가?
- PostgreSQL과 pgvector를 같은 DB에서 무리 없이 사용할 수 있는가?
- 운영 환경에서 보안과 migration 전략을 설명할 수 있는가?

## 2. 평가 범위

### 포함

- 회원가입 / 로그인
- 게시글 CRUD
- 댓글
- 태그
- 검색
- 페이징
- 관리자 권한 분리
- RAG 검색
- AI 답변 초안 생성
- GitHub Issue 생성 승인 플로우
- PostgreSQL/pgvector 스키마
- 운영 보안 정책

### 제외

- 대규모 트래픽 부하 테스트
- 실제 프로덕션 배포
- 장기 운영 모니터링
- 비용 최적화
- 복잡한 멀티 에이전트 워크플로우

## 3. 성공 기준

| 영역 | 최소 성공 기준 |
| --- | --- |
| 인증 | 일반 사용자와 관리자의 권한이 분리된다 |
| 게시판 | 게시글 작성, 조회, 수정, 삭제, 댓글, 검색, 페이징이 동작한다 |
| RAG | 질의와 관련된 문서가 상위 결과에 포함된다 |
| Agent | `answer_only`, `needs_human_review`, `github_issue_recommended`를 구분한다 |
| MCP | GitHub Issue는 관리자 승인 후에만 생성된다 |
| DB | 게시판 데이터와 AI 처리 이력이 같은 PostgreSQL에 저장된다 |
| 운영 | `synchronize: false`와 migration 전략을 설명할 수 있다 |

## 4. 측정 지표

### 정량 지표

- 게시글 목록 조회 응답 시간
- 게시글 상세 조회 응답 시간
- 댓글 등록 응답 시간
- RAG 검색 응답 시간
- AI 검토 전체 응답 시간
- GitHub Issue 생성 응답 시간
- RAG 검색 Top-K 적중률

### 정성 지표

- 답변 초안의 실제 도움 정도
- Agent 판단의 납득 가능성
- 관리자 화면의 사용 흐름 명확성
- 오류 메시지의 원인 파악 가능성
- 보안 정책 설명 가능성

## 5. 평가 방식

각 기능은 최소 3회 반복해서 측정합니다.

```text
1회차: 서버가 막 실행된 상태
2회차: 같은 요청을 반복한 상태
3회차: 다른 테스트 데이터로 실행한 상태
```

외부 LLM 호출이 포함된 기능은 응답 시간이 크게 흔들릴 수 있으므로,
평균값만 보지 말고 최솟값과 최댓값도 함께 기록합니다.

## 6. 평가 결과 해석

성능 평가는 단순히 빠른지 느린지를 보는 것이 아닙니다. 이 프로젝트에서는
아래처럼 해석해야 합니다.

- 게시판 API가 느리면 NestJS/DB 쿼리 문제일 가능성이 높다.
- RAG 검색만 느리면 embedding 생성 또는 pgvector 검색 문제일 수 있다.
- AI 검토가 느리면 LLM 호출 지연이 가장 큰 원인일 수 있다.
- GitHub Issue 생성이 느리면 MCP 서버 실행과 GitHub API 호출 시간이 포함된다.
- DBeaver에서 테이블이 안 보이면 DB 이름과 schema를 먼저 확인해야 한다.
